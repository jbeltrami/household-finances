Lesson 02 · Security

Two Clients, One Boundary

Your app's security does not live in your app. Knowing exactly where it does live is the difference between a codebase that is safe and one that is merely untested.

Where the boundary actually is

Here is the question that decides everything: if a page forgot its .eq("space_id", …) filter, whose rows would come back?

In most apps, everyone's. The filter is the security. Forget it once, in one query, and you have a data breach that looks like a typo.

Not here. Every table in this project has RLS enabled with a policy written in terms of is_active_member(space_id), which collapses to auth.uid() = spaces.created_by. Postgres applies that policy to every query, so the unfiltered query returns your own rows and nothing else. The filter is an optimisation. The database is the boundary.

The mental model

Application code is not trusted to scope its own queries. It is trusted only to say who is asking. The database decides what that person may see. Every security question in this codebase reduces to: does this code path still tell the truth about who is asking?

The key that ignores all of it

Supabase issues you two keys, and the difference is not "one is more secret." It is that they connect as different Postgres roles.

The publishable key is RLS-bound — safe in the browser precisely because policies still apply to it. The secret key connects as service_role, which carries the BYPASSRLS attribute. Supabase's own words:

It will "skip any and all Row Level Security policies."

That is src/lib/supabase/admin.ts. Every query it makes sees every row belonging to every user. It is not a client with extra permissions; it is a client with no boundary at all.

And you cannot delete it. A cron has no session for a policy to bind to. Storage uploads run without a user. Your log and report tables deliberately have no write policies, so that only server code can write them. The admin client is the price of all three.

So the whole thing rests on one rule

The invariant

The admin client may only be reached after a user-session client has established who is calling and which space is theirs. Any spaceId handed to admin-backed code must have come from requireSession — never from a form field, a URL parameter, or any other value the caller chose.

All seven admin-client call sites in this repo satisfy it today. The two crons authenticate by Bearer token and legitimately act for every space. The five server actions resolve the space from the session first.

download-report is the one to memorise, because it shows the shape rather than just obeying it:

  1. Look the report up through the user-session client — RLS decides whether that row is even visible.
  2. Only then use the admin client, to mint a signed URL for the path you just proved the user could see.

The user client answers may they? The admin client does the thing they may. Never the other way round.

The sharp edge

Two helpers — performOverdueAlertSend and performMonthlyReportSend — accept a spaceId and use the admin client. Neither can check that the caller was entitled to that space. Both push the obligation onto their caller, in a comment.

Now picture the change that breaks it. Someone adds an action that takes spaceId from the client and forwards it to one of those helpers. It reads exactly like the existing code. It type-checks. It passes review.

Be exact about the damage, though. Both helpers mail the space's owner, so a forged spaceId sends a stranger their own data — unsolicited mail and a wasted SMTP budget, not a disclosure. The caller never sees anything. The version that would leak outright is the one nobody has written yet: an admin-backed helper that returns data to its caller. The invariant is there to make that function safe on the day it is written.

Nothing in the type system distinguishes a spaceId that came from a session from one that came from a request body. That is the real lesson: the invariant is currently held by comments and habit, not by the compiler.

What this codebase already gets right

Worth knowing, because these are the ones people usually get wrong:

  • The proxy calls getUser(), not getSession(). This is the single most common Supabase/Next.js security mistake. Supabase says to "never trust getSession() inside server code" — it reads from storage without revalidating the token. You are on the right side of it.
  • is_active_member is SECURITY DEFINER STABLE with search_path = public pinned. Without that pin, a caller who controls their own search_path can point the function at a table they wrote.
  • The cron check uses timingSafeEqual. A naive === returns faster on an early mismatch, which leaks the secret one byte at a time.
  • Log and report tables have no write policies at all. A compromised browser cannot forge rows into them, because there is no policy under which a browser may write.
  • The storage bucket is private with deny-all, read through 5-minute signed URLs. A leaked URL expires before it is worth anything.
  • Google OAuth only. No password hashes to leak, no reset flow to attack. The whole category is absent by construction.

What could be better

  1. Nothing rate-limits the email actions. An authenticated user can call the test-alert button in a loop and send unbounded mail through your Hostinger SMTP. The realistic damage is your sending reputation and possibly the account. This is the most concrete gap in the app today.
  2. No security headers. next.config.ts sets none — no CSP, no X-Frame-Options, no Referrer-Policy. A finance app that can be framed is a clickjacking target.
  3. The spaceId invariant is unenforced. Splitting the send helpers into a session-scoped entry point that takes no spaceId and a cron-scoped one that does would make the dangerous call impossible to write.
